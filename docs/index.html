Learning to repair
JAX-to-PyTorch ports.

A SWE-Marathon-inspired task, scaled down to a single GPU and a 4B policy. What outcome-grounded reinforcement learning achieved, where it failed, and what the evidence actually supports.

The guiding question

Does longer-term action value add anything beyond immediate verifier rewards?

Not established by this pilot. The combined trained policy improved numerical held-out coverage from 1/3 to 2/3 tasks at one policy seed. But terminal-only and immediate-reward comparison arms were not run, the critic had only 12 rows, and training diagnostics changed. This demonstrates a feasible learning pipeline—not a causal benefit of the action-value predictor.

01 / Task & scope

Scaling down an ambitious engineering task.

SWE-Marathon’s jax-pytorch-rewrite asks an agent to port a renamed JAX vision-language-action policy to PyTorch, preserve numerical behavior, and optimize inference without breaking correctness. MiniPort is a custom, scaled-down derivative of that task idea: small neural-network components replace the full architecture, making repeated repair rollouts and fine-tuning practical with Qwen3-4B on one GPU. It is not an official SWE-Marathon benchmark result. Original task instructions.

The catalog contains six templates and 18 training configurations. This report measures three families; the current policy schedule uses mlp-0, layernorm-0, and attention-0. Held-out configurations differ in feature width, head count, batch, length, and epsilon.

Measured taskRequired behaviorSubtle contract
MLPReLU first projection, then a second dense projection.Return the hidden activation separately; export dense matrices transposed.
LayerNormNormalize the last axis with population variance; apply scale/bias and a residual projection.Epsilon is inside the square root; output = x + layer @ weight.
Causal AttentionSplit Q/K/V, arrange heads, compute scaled masked softmax, merge heads, project output.Return merged attended values before output projection; mask future keys, including the diagonal as visible.

Nominal training configuration: batch 1, length 4, width 8, heads 2, epsilon 1e−5. Held-out: batch 3, length 7, width 24, heads 3, epsilon 1e−3. Final randomized cases additionally vary batch and sequence length.

02 / Final evaluation

A numerical gain, with unresolved validity.

Fresh paired GPU evaluation, job 6119, finished in 24 minutes 16 seconds. Both conditions used policy seed 42, the same held-out manifest and stored randomized challenges, and an 18-action budget. The trained arm loaded the committed update-16 adapter; the baseline loaded the same immutable base revision without an adapter.

Numerical success: 33.3% → 66.7% (one additional solved task). Mean actions: 5.67 → 4.67, a 17.6% reduction. Fewer actions include earlier termination of unsolved episodes, so they cannot be equated with faster correct solutions.

Strict audited validity: 0/3 → 0/3. Numerical passers have integrity_audit_passes=false and valid=false. The evaluator supplies no human audit, while the verifier requires a complete reviewer-approved audit bound to the exact source hash. This is missing validation, not proof of cheating. Syntax-rejected submissions return before some final fields are populated.

Did inference reach correct solutions faster?

Not demonstrably. Both MLP policies first passed visible checks on action index 1 (the second action); generation time to that point was 46.84 s baseline vs 66.07 s trained. Trained LayerNorm first passed at index 2 after 122.83 s of generation; its baseline never solved it. Neither Attention policy solved the task, and trained Attention spent more generation time despite fewer actions.

Total logged generation time was 653.16 s baseline vs 735.42 s trained. These are single-run model-generation timings, excluding verification and load overhead—not optimized PyTorch program latency. Run order, token lengths, and generation cost confound wall-clock comparisons.

MLP and LayerNorm failures prominently involved malformed Python escapes. Baseline Attention progressed from axis-API errors to invalid Q/K/V reshape sizes; trained Attention stopped at a syntax failure. Thus the held-out Attention result does not test its eventual numerical implementation successfully.

Evidence: all six compact eval records, including hashes, tokens, timings, missing fields, and audit status. The earlier partial update-8 baseline is historical only; the headline comparison uses the fresh paired run.

03 / Project evolution

Failures shaped the experiment.

  1. Initial design and environment. Build a numerical porting testbed with edit/test/stop actions, external verification, compact feedback, protected logs, and matched frozen-policy branches. Terminal-only, immediate-verifier, and action-value reward conditions were implemented; the completed policy run used action-value.
  2. Early training and CNN diagnosis. The first eight optimizer updates included CNN alongside the other families. CNN had 0/8 terminal passes and consumed 144 actions. One recorded failure expected 12 input channels but received 8, exposing confused kernel/channel layout rather than missing error delivery. Diagnostics were strengthened with numerical statistics and an intermediate sign-clipping hint: even correct shapes do not guarantee the right pre-activation intermediate.
  3. Refine diagnostics and focus the schedule. Narrow training to MLP, LayerNorm, and Attention. Strengthen tensor contracts and Attention’s semantic shape ledger. Make negative diagnostic events count under action-value training and add a reflection/termination route for repeated unchanged failures.
  4. Augment stuck-state collection. Mine 13 distinct no-op/error states: five LayerNorm and eight Attention; none from MLP. A local 14B teacher approach was attempted, then stopped. GPT-5.6 Luna supplied externally generated corrections admitted by the verifier. No local 14B teacher was loaded in the final collection job.
  5. Finalize collection and resume. Keep four complete matched states: one LayerNorm and three Attention. With two actions and four continuations each, this produced 32 rollouts and eight teacher rows. Combine with four ordinary rows, refit the critic, and continue from update 8 to update 16. Job 6107 completed the additional training in 7 h 1 m 58 s; peak CUDA allocation was 12.55 GiB.
  6. Operational debugging and final eval. Resuming with total target 8 restored eight updates and exited without training; increasing the target to 16 fixed that configuration mistake. Controlled Slurm probes isolated explicit --export=ALL,... as a launch-failure trigger on this cluster. Shell-prefix environment assignments worked. The final fresh paired eval completed after correcting submission style.

04 / Learning pipeline

Ground every stage in executable outcomes.

Frozen-policy collection → verifier-filtered teacher actions → empirical action-value fitting → QLoRA policy updates → paired held-out evaluation

1. Collect state/action continuations

Save the current source, observable history, remaining action budget, task, and completion. Propose two distinct actions at the same state; force each action, then continue with a frozen policy under matched seed schedules. Grade eventual terminal success. Store success counts and valid continuation counts; exclude environment outages and avoid counting identical actions as distinct evidence.

2. Add teacher-corrected hard states

Mine repeated unchanged-source/error states from training traces, not held-out eval. Verify the proposed teacher edit before admitting it. Then compare the original student action and the teacher action at the exact same state with the same continuation seeds and remaining budget. In all four retained states, student continuations scored 0/4 and teacher continuations 4/4. These are noisy, policy-conditional outcomes, not universally calibrated probabilities.

All 13 external corrections were verifier-approved, but only four states contributed completed pair labels. Those 13 files reduce to two distinct correction-source hashes—one LayerNorm solution and one Attention solution—so they should not be presented as 13 independent solution strategies.

3. Fine-tune the 4B policy

Qwen/Qwen3-4B-Instruct-2507 runs with NF4 4-bit base weights and rank-8 LoRA adapters. QLoRA keeps the quantized base frozen; only adapters update. Settings include 4,096-token context, 1,024 generated tokens/action, temperature 0.6, group size four, gradient accumulation eight, AdamW learning rate 1e−5, and sequential rollouts within a 16 GiB CUDA cap. Optimizer/scaler state and the next update index are checkpointed.

4. Evaluate without learning from held-out outcomes

Load the same immutable base revision, with or without the adapter. Run held-out tasks with identical generation settings and budgets, then check both held-out-seed parity and additional randomized cases. There is no critic-guided inference or policy update during evaluation. Human artifact review is a separate, still-outstanding criterion.

What is hidden? Ground-truth tensors are computed by the trusted JAX verifier process and never included in worker requests. The candidate receives inputs and parameters, returns actual tensors, and is graded externally. However, the starter includes JAX equations as reference comments; the reference algorithm is intentionally visible. “Hidden reference” here means protected expected outputs and external grading—not a completely secret algorithm or a hardened host sandbox.

Implemented in train.py, teacher_collect.py, and gpu_eval.py.

05 / Predicting eventual success

A lightweight, outcome-trained action-value model.

The intended quantity is Qπ(s,a,b): the probability of eventual verifier success after taking action a at code state s with budget b, then following frozen policy π. The implementation encodes the prompt and proposed action as normalized, hashed token-bigram counts: 512 features → 64-unit tanh hidden layer → sigmoid output. Source, history, and budget are represented through prompt text, not dedicated semantic features.

class ActionValue:
    def __init__(self):
        self.model = torch.nn.Sequential(
            torch.nn.Linear(FEATURES, 64),
            torch.nn.Tanh(),
            torch.nn.Linear(64, 1))

    def predict(self, prompt, action):
        self.model.eval()
        with torch.no_grad():
            return self.model(features(prompt, action)).sigmoid().item()

Excerpt from action_value.py (formatting condensed; FEATURES = 512).

Targets are successes/count. Fitting uses count-weighted binary cross-entropy on empirical rates and a task-family split. The final dataset has 12 rows / 48 continuation outcomes: ten rows for fitting and two MLP rows for validation. Validation Brier error versus empirical rates is 0.0721. Both validation rows have 4/4 successes, so this small validation set cannot establish negative-example discrimination or calibration. Dataset hashing prevents loading a critic against different eligible rows.

alternative = policy.generate(task, snapshot.source,
    snapshot.history, snapshot.remaining, seed + 100000 + index)
qa = value_model.predict(completion.prompt, completion.text)
qb = value_model.predict(alternative.prompt, alternative.text)
value_advantage = (qa - qb) / 2

# In the policy-gradient update:
credit = advantage + value_coefficient * step["value_advantage"]

Condensed excerpts from rollouts.py and rl.py.

Instead of repeatedly adding raw predicted success, the policy gets centered credit (Q(a) − Q(alternative))/2. This avoids directly rewarding lingering in states that merely look promising. Generating an alternative for each executed action adds training compute. The critic is frozen during the policy phase; its labels came from an earlier policy checkpoint, so policy drift can weaken its relevance.

Did it improve RL or inference? The combined pipeline produced encouraging MLP/Attention training trends and one additional held-out numerical pass. No terminal-only or immediate-reward-trained controls exist, so the action-value contribution is unknown. There is no demonstrated general inference speedup. Teacher corrections trained the critic indirectly; they were not used for language-model SFT or direct teacher imitation.

06 / Reward & optimization

RLOO-style RL—not GRPO or policy SFT.

Each group contains four trainable trajectories. A rollout’s advantage is its shaped terminal reward minus the average of the other three rewards. Generated action tokens receive policy-gradient credit with a frozen-base KL penalty. The implementation uses an on-policy REINFORCE/RLOO-style loss; it does not use GRPO’s group-standard-deviation normalization or a PPO-style clipped probability-ratio objective. The supervised component is the small critic, not instruction SFT of Qwen.

# Terminal outcome, only after stopping:
training_reward = float(terminal_report["passed"])

# action_value condition: negative diagnostic events only
diagnostic_credit = sum(
    min(0.0, value)
    for record in trajectory["records"]
    for value in record["diagnostic_reward"]["events"].values()
)
episode_reward = training_reward + 0.1 * diagnostic_credit

# Leave-one-out trajectory advantage for a group of K rollouts
advantage_i = reward_i - sum(other_rewards) / (K - 1)

# Additional centered critic credit, coefficient 0.25
credit = advantage_i + 0.25 * value_advantage

Reading aid for the executed action-value condition. The actual implementation normalizes the token loss across trajectories and accumulation groups; its sampled KL term is exp(log p_ref − log p_policy) − (log p_ref − log p_policy) − 1, with coefficient 0.01.

Base terminal reward is 1 for passing independent randomized training-terminal checks, otherwise 0. It is zero before stopping, so a pending zero is not a failed episode. Environment outages invalidate the sample instead of teaching the policy that infrastructure failure is its fault.

Diagnostic event values include repetition −0.25, lost gates −0.75 each, immediate revert −0.15, premature stop −2.0, and signed numerical-change credit capped at ±0.25. In the current action-value arm, only negative event components contribute, scaled by 0.1. Positive first-time gate bonuses belong to the implemented immediate-reward arm, not this completed run. Terminal correctness remains primary, but diagnostic penalties can accumulate and should be ablated rather than assumed harmless.

The generic tracker also defines a premature-profile penalty, but the active edit/test/stop action interface has no profile action. It is a design hook—not an observed optimization event.

08 / Reward hacking & execution safety

Separate correctness from apparent progress.

The reward is grounded in the submitted program’s outputs, not a model’s self-report. Intermediate progress alone is insufficient for terminal success. Topology, exact parameter mapping, layer parity, end-to-end output, and repeat determinism must pass in order, across multiple seeded cases. Floating-point checks require finite float32 tensors with correct shapes and tolerances atol 2e−5 / rtol 2e−4; fresh randomization changes batch and sequence length.

  • Parameter mapping: exporting transposed weights correctly does not imply those weights are used correctly internally. The layer and output gates independently check the resulting computation.
  • Intermediate semantics: returning an output projection as Attention’s “layer,” or applying CNN activation too early, can produce plausible shapes while violating the intended intermediate contract.
  • Determinism: repeated output checks detect dependence on uncontrolled randomness. Sampling templates use supplied random draws, rather than rewarding whichever sample happens to look best.
  • Generic behavior: randomized batch/length cases challenge nominal-shape hardcoding. Checking parameter keys, dtypes, all returned values, and multiple seeds raises the cost of fixed-output shortcuts.
  • Admission and provenance: restrict edits to one non-symlink source file; scan imports and dynamic execution/I/O facilities; snapshot and hash exact source; bind review decisions to artifact hashes. Static analysis is conservative, not a proof of semantic safety.

Docker isolation exists—but was not used for these GPU results.

The repository’s Docker verifier runs candidate code without JAX, reference packages, or hidden targets in the container. It uses network none, read-only root and binds, dropped capabilities, no-new-privileges, a non-root user, bounded PIDs/CPU/memory, a small tmpfs, and cleanup on timeout. The image ID is recorded. This boundary is the intended safer path for untrusted submissions and repeatable production execution.

Actual training, teacher-pair collection, and job-6119 eval used SubprocessBackend. That path runs a CPU worker in a temporary directory with Python isolated-import mode, hides CUDA, limits runtime/output, and cleans process groups. It still executes under the host user with inherited environment and no OS-level filesystem/network isolation. It is not a security sandbox, even if the numerical grader is logically external.

For production, use hardened container or stronger VM isolation, strip secrets from worker environments, avoid mounting the repository or targets, pin runtime/image digests, retain request/response provenance, and scale disposable workers independently from the GPU policy. Those are next deployment requirements, not completed production guarantees. Verification implementation.

09 / Non-obvious findings

The harness matters as much as the optimizer.

  • Valid JSON can contain invalid Python. Literal backslash-n sequences inside a source string survived submission and caused syntax failures. This dominated several held-out outcomes. Do not blindly unescape source: backslashes can be legitimate Python string contents. Stronger source syntax diagnostics and response validation are warranted.
  • Population variance is not enough. One LayerNorm rollout used sqrt(var) + epsilon rather than sqrt(var + epsilon), despite its comment stating the correct formula. It missed tolerance on 46.9% of values with maximum absolute error 0.001237. A shape-only recovery prompt cannot fix numerical-contract ambiguity.
  • Tensor stride and axis semantics differ. A view after permutation may require reshape or contiguity. JAX-style multi-axis transpose must become PyTorch permute. Nominal heads/sequence dimensions that accidentally align can hide mistakes until held-out sizes differ.
  • API/build bugs can mask numerical competence. register_buffer requires an appropriate nn.Module object; torch.tensor has no shape keyword. Undefined names and source syntax can prevent the numerical verifier from reaching useful gates.
  • Unchanged recovery edits wasted compute. Hash/error-signature reflection and subsequent termination curtailed repeated failures. Yet 19 late rollouts still required that termination, and some changed-source repetitions extended further. Better failure-type-specific guidance remains needed.
  • Critic validation was too thin. Only two all-positive MLP validation rows and reused correction implementations make the reported Brier score insufficient evidence of a useful out-of-family ranking model. More diverse negatives, independent validation continuations, and stale-policy audits are needed.
  • A pass field is not audited validity. The grader’s numerical passed flag can be true while valid is false. The summary reports numerical automated passes; an explicit artifact-bound human audit is required for strict final validity. Dashboard/report labels must not conflate them.
  • Infrastructure can look like training failure. An exhausted update target silently produces no new loop iterations. Explicit Slurm export arguments reproduced pre-script cancellations even in hostname-only probes; prefixing environment variables worked. The underlying cluster-side reason remains undiagnosed.

Was there premature optimization or reward hacking?

No convincing intentional hacking or speed-optimization case was established. Repeated no-op edits and revisiting already-correct code were observed, but are inefficiency/failure modes rather than proof of reward exploitation. A LayerNorm repair also added dimension slicing that was unnecessary for canonical fixtures; passing tests should not be taken as proof that such fallbacks are generically correct. The report does not infer motives from these traces.

10 / Conclusion & reproduction

Feasible RL. Unproven action-value advantage.

This project showed that a 4B model can participate in a complete single-GPU, verifier-grounded code-repair learning loop within the memory budget. Teacher-filtered actions generated strongly contrasting continuation labels. The combined trained policy solved one additional held-out family numerically in the final three-task, one-seed evaluation.

It did not establish that learned longer-term credit beats immediate verifier rewards, that repairs become uniformly faster, or that the policy solves the original SWE-Marathon task. Attention remains unsolved held-out, and strict artifact validity remains unaudited.

  1. Complete artifact-bound reviews of numerical passers; repeat verification using the container boundary without changing the frozen submission.
  2. Repair source-format and numerical-guidance weaknesses, then freeze the harness before collecting fresh comparable runs.
  3. Compare frozen baseline, terminal-only, immediate-verifier, and action-value policies under matched training budgets and several seeds. Add an action-value-without-diagnostic-shaping ablation.
  4. Collect dozens of positive/negative actions per family and diverse bug states. Evaluate ranking/calibration on independent continuations and refresh labels as the policy changes.
  5. Measure solve rate, actions and tokens to first correct solution, and generation-plus-verifier time separately. Report failures as unsolved, not fast solutions.
  6. If direct teacher correction learning is desired, add a separately identified SFT or preference-learning arm; it is not part of the current run.

11 / Relevant literature

Methods and context.

  1. SWE-Marathon and JAX-to-PyTorch rewrite task (2026). Source of the task framing; MiniPort is a custom small-scale testbed, not a reported official benchmark solution.
  2. Reward Models in Deep Reinforcement Learning: A Survey (2025). Context for reward-model design and evaluation; motivating literature, not an algorithm implemented verbatim here.
  3. Ahmadian et al. (2024), Back to Basics: Revisiting REINFORCE Style Optimization for Learning from Human Feedback in LLMs. Relevant precedent for simpler REINFORCE/RLOO-style optimization; this project uses executable outcomes rather than human preferences.
  4. Dettmers et al. (2023), QLoRA: Efficient Finetuning of Quantized LLMs. Quantized frozen-base, low-rank adaptation enables the single-GPU policy update setup.
  5. Shao et al. (2024), DeepSeekMath. Introduces GRPO, a useful comparison method. GRPO was not implemented in the current pipeline.
  6. Schulman et al. (2017), Proximal Policy Optimization Algorithms. Context for clipped policy optimization; the current loss is not PPO.
  7. Lightman et al. (2023), Let’s Verify Step by Step. Relevant outcome-versus-process supervision distinction; this project labels executable continuations, not human reasoning steps.
